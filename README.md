# Проект "Food Integrator"

## Описание проекта
Это приложение на Spring Boot, реализующее каркас системы для интеграции и вывода данных о еде. Проект спроектирован с разделением на слои (Контроллер -> Сервис -> Модель) и служит для демонстрации применения базовых принципов объектно-ориентированного проектирования.

Архитектура системы и связи между компонентами предварительно зафиксированы в UML-диаграмме в файле `food-integrator.plantuml`.

---

## Анализ принципов проектирования (SOLID, KISS, DRY)

### 1. Принципы SOLID

* **S (Single Responsibility Principle — Единственная обязанность):**
  Каждый класс в проекте отвечает строго за одну задачу.
  - `FoodController` — отвечает только за обработку входящих HTTP-запросов и возврат ответов. Он не знает, откуда берутся данные и как они обрабатываются.
  - `FoodService` — содержит логику управления данными о еде. Он не знает про существование веб-протоколов.
    *Если бы принцип не соблюдался:* Весь код был бы написан в одном классе. Контроллер сам бы создавал списки объектов, обрабатывал их и отдавал клиенту, что сделало бы код кашей.

* **O (Open/Closed Principle — Открытость / Закрытость):**
  Архитектура готова к расширению без изменения существующего кода. Логика работы с едой вынесена в `FoodService`. Если в будущем логика интеграции изменится (например, данные будут браться из базы данных или внешнего API), мы сможем внедрить новый сервис через интерфейс, не меняя код в `FoodController`.
  *Если бы принцип не соблюдался:* При изменении источника данных нам пришлось бы полностью переписывать внутренности контроллера.

* **L (Liskov Substitution Principle — Подстановка Лисков):**
  Компоненты системы взаимодействуют по четко установленным контрактам. Любая новая реализация логики сервиса сможет заменить текущую без поломки работы `FoodController`.

* **I (Interface Segregation Principle — Разделение интерфейсов):**
  В проекте используются компактные интерфейсы и классы, решающие конкретную задачу. Компоненты системы не перегружены лишними неиспользуемыми методами.

* **D (Dependency Inversion Principle — Инверсия зависимостей):**
  Классы не создают зависимости жестко внутри себя. Связь между слоями настраивается через Dependency Injection фреймворка Spring. `FoodController` запрашивает `FoodService` через конструктор.
  *Если бы принцип не соблюдался:* Внутри контроллера была бы жесткая привязка через `new FoodService()`, что сделало бы компоненты намертво сцепленными и не позволило бы тестировать их изолированно.

---

### 2. Принцип KISS (Keep It Simple, Stupid — Делай проще)
Код написан максимально просто и прямолинейно. Архитектура не перегружена сложными паттернами "ради паттернов". Для обмена данными используются стандартные структуры, а логика в сервисе написана понятным и легко читаемым языком.

---

### 3. Принцип DRY (Don't Repeat Yourself — Не повторяйся)
В проекте полностью отсутствует дублирование кода. Главный пример применения DRY — подключение библиотеки **Lombok** для классов в пакете `model`. С помощью аннотаций (`@Data` / `@Getter` / `@Setter`) Lombok сам генерирует методы доступа, избавляя проект от ручного написания сотен строк одинаковых геттеров, сеттеров и конструкторов для моделей еды.

---

## Вывод
Соблюдение принципов SOLID, KISS и DRY в рамках проекта `food-integrator` полностью целесообразно. Такое разделение кода на слои гарантирует, что небольшое приложение легко читать, поддерживать и расширять в будущем.
